# Lean application workflow

This mode replaces the upstream auto-pipeline/pipeline/pdf/apply workflow when `pipeline.mode: lean`. Load only this file, the data-root `modes/_custom.md`, `config/profile.yml` and `cv.md`; no scoring or evaluation prompts. System factual and no-submit boundaries still apply. One job at a time; no automatic delegation.

1. **Pre-screen.** Reuse a supplied/cached employer JD. For a URL use `node browser-extract.mjs <url> --mode jd` once (Workday uses its public CXS endpoint). Save the full text and original URL in `jds/` and a job JSON under `data/lean/` with `{url,company,title,country,text,metadata_only:false}`. Do not put page text into shell code. On extraction failure ask for pasted JD; do not begin a browser retry loop. A repository listing is not a verified live opening. Read the JD for explicit hard constraints including authorization, future sponsorship, non-internship experience, degree, graduation, start date and location. Record only unambiguous structured constraints in job JSON (supported fields are in `lib/lean-screen.mjs`). Run `node lean-prescreen.mjs <job.json>`. `skip`: show quoted reason and stop. `needs-review`: resolve material questions with the user; silence is no answer. Confirm unparsed degree/experience alternatives yourself from the source; ask if uncertain. Preferred qualifications do not become hard requirements. No numerical fit score.
2. **Buildcv.** Rephrase and select source-backed content to match the JD; never add a technology, achievement, metric, job or date from the JD. Preserve reverse chronology and canonical titles. Create one compact payload for `build-cv-html.mjs` under `output/`; inspect `lib/cv-payload-schema.mjs` only if the schema is needed. Candidate uses `{name,email,phone?,location?,linkedin?:{url,display},github?:{url,display}}`; experience uses `{company,role,dates,location?,bullets}`; projects use `{name,description?,bullets?,tech?,url?}`; education uses `{title,org,year,location?,description?}`; skills use `{category,items}`. `cv.show_location:false` omits candidate.location; never substitute a hiring city's address. `cv.projects:auto` selects truthful relevant projects, `omit` excludes them, a list selects names; explicit user request wins. English JD → English CV; chat summaries can be Chinese. Reuse an approved base payload when available: emit only a JSON object of changed fields and run `node lean-buildcv.mjs --base <base.json> --patch <patch.json> <output-stem>`. Objects merge, arrays replace, and null removes a field. Read cv.md for source facts even when reusing a base; a prior CV is not an independent factual source. Without a base, run `node lean-buildcv.mjs <payload.json> <output-stem>`; the existing renderer performs deterministic fact, ordering, layout and page checks. Use the readable lean template (11pt body, bundled static fonts). Keep one page by selecting relevant content, not reducing the font. Inspect the rendered PDF once, fix only actual defects. Batch independent context reads and reuse the captured JD; do not narrate or re-read the same content after each tool call. No LLM eval, cover letter or report prerequisite. If material facts are missing, ask before building.
3. **Chromium sign-in and upload.** Only when the user requests an actual application destination, run `node lean-handoff.mjs --url <employer-application-url> --resume <absolute.pdf> --upload`. It launches a dedicated persistent Chromium profile inside the data root (no CDP/real Chrome profile), then the user signs in, handles MFA/CAPTCHA and navigates to Resume/CV upload. The helper looks for one explicitly résumé-labelled file input, sets that one file once, then stops inspecting the page. If ambiguous, it leaves upload to the user and prints the PDF path. No automated typing, dropdowns, generic click loops, form POST or Submit. With no destination authorization generate the CV and give the path only.
4. **Hand over.** Provide the exact PDF link, application URL and remaining questions; keep state `ready` or `uploaded`, never `Applied` from an upload. If the user later confirms submission, use the upstream tracker writer with score `N/A`, no invented evaluation report. Reuse saved JD/PDF on resume rather than repeating work.

For discovery use `$career-ops-job-ingestion`; do not use upstream scored scan/batch workers. The local ingestion queue is `data/lean/jobs.json` plus `data/lean/shortlist.md` and remains separate from the upstream scored tracker.
